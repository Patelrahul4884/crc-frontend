Engineering Rationale

Engineering Decisions

Architectural justifications, alternatives evaluated, and production trade-offs.

Decision 01

Why Serverless Architecture?

Chosen Because

Serverless services avoid always-on compute infrastructure and fit the low and variable traffic profile of this portfolio. Automatically scales with incoming request volume without provisioning virtual machines or managing operating system patching.

Alternatives Considered

Single EC2 instance (t4g.nano) or ECS Fargate container. Rejected due to fixed ongoing compute costs regardless of traffic, required OS maintenance, and continuous idle capacity.

Trade-Off & Mitigation

Cold starts can introduce additional latency. The Lambda function is kept lightweight to reduce unnecessary execution overhead.

Decision 02

Why CloudFront Edge CDN?

Chosen Because

Keeps the S3 origin bucket private via Origin Access Control (OAC). Terminates TLS 1.3 at edge locations and distributes cached content through edge locations, reducing the distance between users and the origin, with built-in AWS Shield Standard DDoS mitigation.

Alternatives Considered

Direct S3 Static Website Hosting. Rejected because S3 web endpoints do not support custom domain SSL/TLS certificates natively and require public read bucket access.

Trade-Off & Mitigation

Cached content propagation delay on updates. Mitigated by automated CI/CD cache invalidation (`/*`) via GitHub Actions upon deployment.

Decision 03

Why Declarative Terraform?

Chosen Because

Explicit state-driven infrastructure as code. Enables deterministic preview (`terraform plan`), full auditability, automated resource teardown/recreation, and version-controlled history in Git.

Alternatives Considered

AWS Management Console (ClickOps) or AWS SAM. Console lacks repeatability; SAM is specialized for Lambda but less flexible for managing multi-region ACM certs and Route 53 zones together.

Trade-Off & Mitigation

State file management and locking complexity. Mitigated by storing remote state in S3 with DynamoDB state locking to prevent concurrent modifications.

Decision 04

Why DynamoDB NoSQL?

Chosen Because

Supports atomic counter updates (`UpdateItem` with `ADD visitor_count :inc`), guaranteeing concurrency safety when visitors browse concurrently without requiring application-level mutexes or database locks.

Alternatives Considered

Amazon RDS (PostgreSQL/MySQL). Rejected because relational databases require VPC networking, connection pooling management, and ongoing minimum compute charges.

Trade-Off & Mitigation

Limited query capability compared to SQL. Completely acceptable since the telemetry schema requires only fast single-key lookups and atomic updates.

Decision 05

Why GitHub Actions CI/CD?

Chosen Because

Seamless native repository integration with zero self-hosted infrastructure. Automatically syncs frontend builds to S3 and triggers CloudFront cache invalidation upon push to `main`.

Alternatives Considered

AWS CodePipeline / CodeBuild or manual AWS CLI uploads. AWS CodePipeline introduces excess console switching and configuration overhead for lightweight static assets.

Trade-Off & Mitigation

Dependency on GitHub runner uptime. Mitigated by storing standard AWS CLI deployment scripts that can execute locally with one command if needed.

Cloud Resume Challenge — Technical Case Study

AWS Serverless Architecture · Terraform IaC · CI/CD Automation

Project Overview

The Cloud Resume Challenge is a hands-on, multi-discipline cloud engineering project designed to demonstrate mastery across full-stack cloud computing on Amazon Web Services (AWS). Rather than building a typical static resume, this project requires architecting a production-grade, highly available, secure web application with global edge delivery, serverless APIs, persistent state tracking, infrastructure as code, and continuous deployment pipelines.

GitHub: crc-frontend ↗ GitHub: crc-terraform ↗

Dual-Layer Architecture

The architecture is intentionally segregated into two decoupled tiers:

  • Static Presentation Tier: Amazon S3 bucket with all public access blocked, fronted by Amazon CloudFront with Origin Access Control (OAC), TLS 1.3 encryption via AWS Certificate Manager (ACM), and custom DNS resolution managed by Amazon Route 53.
  • Serverless Telemetry Tier: Single-page JavaScript client initiates asynchronous GET requests to Amazon API Gateway, which invokes an AWS Lambda function running Python to perform an atomic increment and read operation against an Amazon DynamoDB table.

AWS Infrastructure Services

AWS Service Role in Architecture Security & Configuration Details
Route 53 DNS Management Alias A-Record pointing to CloudFront distribution, automated ACM certificate validation.
CloudFront Edge CDN & Security Edge caching, Origin Access Control (OAC) to keep S3 private, TLS 1.3 termination.
Amazon S3 Static Asset Storage Bucket policy strictly restricts read operations to the CloudFront distribution principal.
API Gateway Serverless REST API CORS headers configured (`Access-Control-Allow-Origin: *`), Lambda proxy integration.
AWS Lambda Event-Driven Compute Python runtime, minimal footprint, scoped IAM policy restricted only to the DynamoDB table.
DynamoDB NoSQL Key-Value Store On-Demand capacity billing, atomic update expressions to guarantee race-condition safety.
AWS IAM Access Control Strict least-privilege execution roles for Lambda and CI/CD deployment credentials.

Infrastructure as Code (Terraform)

All AWS infrastructure components are declared, provisioned, and managed through HashiCorp Terraform in the crc-terraform repository.

# DynamoDB Atomic Counter Mutation Example (Python Lambda) response = table.update_item( Key={'id': 'visitor_count'}, UpdateExpression='ADD visitor_count :inc', ExpressionAttributeValues={':inc': 1}, ReturnValues='UPDATED_NEW' ) visitor_count = int(response['Attributes']['visitor_count'])

Using Terraform eliminates manual ClickOps in the AWS console, guarantees that configuration drift is immediately visible via terraform plan, and ensures reproducible deployments across development and production environments.

Automated CI/CD Delivery Pipeline

Continuous integration and deployment is managed via GitHub Actions:

  • Frontend Pipeline: On push to main branch, GitHub Actions executes validation, synchronizes static HTML/CSS/JS assets to the S3 bucket using aws s3 sync, and issues an immediate CloudFront cache invalidation (aws cloudfront create-invalidation --distribution-id ... --paths "/*").
  • Backend Pipeline: Validates Lambda Python code, runs test assertions, and packages and deploys the function update.

Production Lessons Learned & Engineering Insights

  • 1. CloudFront Certificate Regionality Constraint

    AWS Certificate Manager (ACM) certificates used with CloudFront distributions must be provisioned in the us-east-1 (N. Virginia) region regardless of where other regional resources reside. Handled cleanly in Terraform via multi-provider aliases.

  • 2. Origin Access Control (OAC) Migration

    Legacy CloudFront setups relied on Origin Access Identity (OAI). Implementing the modernized Origin Access Control (OAC) provides stronger cryptographic signing (SigV4), SSE-KMS support, and guarantees that S3 bucket policies completely block direct public access.

  • 3. Concurrency Safety with Atomic DynamoDB Increments

    A naive read-increment-write approach causes lost updates during simultaneous visits. Utilizing DynamoDB's native UpdateExpression='ADD visitor_count :inc' performs the increment atomically on the database storage node, preventing race conditions without requiring application-level locking.

  • 4. Edge Cache Invalidation Lifecycle

    Without automated cache invalidation, browsers continue receiving stale cached versions until edge TTL expires. Automating invalidations in the GitHub Actions workflow ensures rapid distribution of production updates.
